# Ожидания: перезапуск линии Sol для v9 (1.4.1)

Записано до запуска.

## Зачем

Пользователь видел сбой инструментов: хуки в `~/.codex/hooks.json` ссылались на удалённый Node 24.9.0. Серия v9 (`../2026-10-20-v9/`) шла после удаления этого Node. По её журналам влияния на ячейки не видно, но пользователь решил линию Sol перемерить.

## Как

- 12 ячеек: v9 (`88fe38e`), модель Sol, 4 задачи × 3 повтора, по 4 параллельно.
- Codex 0.163.0 и Node v24.22.0 — как у v9. Слой запуска `workforce-economy`.
- Колонки «без кита» и v8 берутся из их прогонов. Первый прогон v9 по Sol сравнивается вручную.

## Что считается

- Контракт 12 из 12, как у первого прогона.
- Цена и время линии Sol сравниваются с первым прогоном v9: $2.68 и 39,6 мин.
- Если разница линии меньше 15% и контракт тот же — первый прогон подтверждён, и README остаётся.
- Если больше — README, графики и доказательства по Sol обновляются по перезапуску, выходит патч 1.4.2.

## После запуска (дописано после прогона)

- Ячейка `big-v9-sol-r2` упала на втором запросе: API ответил «Selected model is at capacity», Codex завершил ход за 13 с ($0.03). Кит в ней не работал. Ячейка запущена ещё раз отдельно, с тем же окружением (Codex 0.163.0, Node v24.22.0, слой `workforce-economy`); в таблицах — повторная ячейка.
- В этот день API Sol отвечал медленнее: при близком числе запросов среднее время запроса 12–16 с против 7–9 с у первого прогона v9, скорость вывода около 47 ток/с против 66–87. Время линии поэтому выше, и его сравнение с первым прогоном не чистое.
- Ошибок хуков и инструментов нет ни в одной ячейке; событие ошибки API одно — в упавшей ячейке.
- Итог: контракт 12 из 12; линия Sol $3.32 и 68,7 мин против $2.68 и 39,6 мин у первого прогона, разница больше 15% — README, графики и доказательства по Sol обновляются по перезапуску (патч 1.4.2).
